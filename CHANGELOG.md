# Changelog

All notable changes to VibeChem are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `scripts/bench.py`: speed-up (1 vs N workers) and determinism benchmark of a nested-CV pipeline with an optional `cProfile` run, a nightly `bench` job on 3 OS and the profiling report `docs/spikes/profiling.md` (speed-up 2.4x at 8 workers, below the 4x target, see R65).
- Python API and command line: `from vibechem import Pipeline` (`load`, `validate`, `run(data={dataset_id: dataset})`) and `vibechem run FILE --data DATASET_ID=table.csv`, `vibechem validate FILE`, `vibechem blocks list`; new source block `data.dataset` and `vibechem_core.blocks.default_registry()`.
- Repository skeleton: package folders, legal and citation files, contribution guide, PR template and issue forms.
- `scripts/merge_step.py`, the guarded merge of step PRs into their phase branch.
- Python uv workspace (`vibechem-core`, `vibechem-engine`) on Python 3.14 with ruff, pyright (strict), pytest and pre-commit.
- `scripts/check.py`, the local quality check that prints the health summary (`--fast`, `--only`, `--verbose`; full log in `reports/check.log`).
- Desktop app workspace in `app/`: Electron 45 + electron-vite, React 19 with strict TypeScript, Tailwind 4 with the UI_GUIDE design tokens, shadcn/ui config, bundled fonts, English/Japanese/Vietnamese strings, ESLint, Prettier and Vitest. `scripts/check.py --only app` runs the app's lint, type check and tests.
- Native C++20 package skeleton `vibechem-native` (CMake + scikit-build-core + nanobind, built by `uv sync`) with a stub `row_mean` kernel, automatic NumPy fallback when the extension is missing, Catch2 and Python equivalence tests. `scripts/check.py --only native` checks its Python wrapper and tests.
- QA tooling: `vibechem_core.testing` (tolerance, reference, golden-file and hypothesis helpers); `scripts/check.py` now checks package boundaries (import-linter), writes `reports/reference_report.md` and enforces per-package coverage thresholds.
- Reference datasets in `testdata/`: gasoline NIR (60 spectra with octane numbers) and olive oil FTIR (120 spectra from four countries). Their sources, licences and published results are in `testdata/datasets/PROVENANCE.md` and `testdata/expected/`; `vibechem_core.reference_datasets` loads them.
- Engine API walking skeleton: `python -m vibechem_engine.api` serves `/api/v1/health`, `/api/v1/blocks` (SNV only) and the temporary `/api/v1/skeleton/run` on a random loopback port, protected by a per-launch session token and an Origin check, and announces port and token on stdout.
- Desktop app walking skeleton: in development the app starts the engine itself and shows a fixed Dataset → SNV pipeline on a canvas; Run loads the gasoline NIR spectra and plots them raw and after SNV. The first end-to-end test (Playwright, Electron) checks this flow on Windows, macOS and Linux.
- Installers for Windows (NSIS), macOS (dmg, Apple Silicon) and Linux (AppImage, deb), built in CI. They bundle the engine as a standalone program, so no Python install is needed. Each build is smoke-tested: the bundled engine must report ready, and the packaged app must run the Dataset → SNV pipeline. The builds are unsigned for now.
- `vibechem_core.data.SpectralDataset`: an immutable container for spectra (signal values, spectral axis with unit, signal unit, sample IDs, source-row index, groups, Y with units, classes, metadata columns, pixel layout, processing history). It checks its inputs and keeps every annotation aligned with the rows when signals are replaced (`with_X`) or rows are selected (`subset`).
- Block contract for developers (`vibechem_core.block`, `vibechem_core.registry`, `vibechem_core.errors`): a block declares its ports, typed parameters and metadata, implements `fit` and `apply` (fitted blocks) or `apply` only, and keeps any fitted state as JSON values plus arrays. A registry lists blocks with their metadata, and errors carry the codes from the error catalogue.
- Fitted block state can be saved and loaded as JSON plus `.npy` files, never pickle (`vibechem_core.block.save_state`/`load_state`). `vibechem_core.wrap.TransformerBlock` turns a scikit-learn-style transformer into a fitted block whose state is saved the same way. `vibechem-core` now depends on scikit-learn 1.9.
- Block parameter schema: each parameter has a type (whole number, number, yes/no, choice or text), optional bounds, unit, odd-only rule, a rule linking it to another parameter, and a condition for when it is shown. `BlockMeta.to_detail_dict()` gives the full `/blocks/{id}` description, `vibechem_core.block.parse_params` checks parameter values from a pipeline and reports the first problem as `BLOCK_PARAM_INVALID`, and `vibechem_engine.api.schemas` holds the matching pydantic models and JSON Schema.
- CSV, TSV and Excel (`.xlsx`) import for developers: `vibechem_core.io.read_table` reads a table and suggests which columns hold the sample ID, groups, classes, Y values, other metadata and the spectra (with a guessed axis unit). It skips `;` and `#` comment lines, reads headerless axis-plus-spectra files such as Bruker `.dpt`, and warns about repeated sample IDs and non-numeric spectral values. Excel files are read with their saved cell values; formulas are not evaluated. `vibechem-core` now depends on openpyxl 3.1.
- JCAMP-DX (`.jdx`, `.dx`) and Galactic SPC (`.spc`) import for developers: `vibechem_core.io.read_jcamp` and `read_spc` return the same table as the CSV reader, one row per spectrum, with the axis unit taken from the file. Several files can be read at once with `read_files`: their rows are stacked with a file-name column, and spectra on different axes are aligned on the combined axis (gaps left empty, with a warning that they need interpolation). Not yet supported: JCAMP-DX compound files and peak tables, and the old SPC formats. `vibechem-core` now depends on jcamp 1.3.
- Vendor file import for developers: Thermo OMNIC `.spa`, PerkinElmer `.sp`, Renishaw WiRE `.wdf` and Bruker OPUS (`.0`, `.1`, …) files are read into the same table as the other readers (`read_spa`, `read_perkinelmer`, `read_wdf`, `read_opus`, and `read_file`/`read_files` by extension). WDF series give one row per spectrum. For OPUS, `read_opus` reads the file's first spectrum by default, skipping interferograms and phase data, and can pick the absorbance, sample or reference block instead. Not yet supported: WDF maps, OPUS data series and PerkinElmer `.fsm` images. `vibechem-core` now depends on brukeropus 1.4.
- First preprocessing blocks for developers: range cut (`preprocess.cut`, one or more axis ranges, bounds inclusive), Standard Normal Variate (`preprocess.snv`, ddof 0 or 1), Multiplicative Scatter Correction (`preprocess.msc`, fitted on training rows; reference = mean training spectrum or a spectrum you connect) and polynomial detrend on the real axis (`preprocess.detrend`). A constant spectrum, or one whose MSC slope on the reference is zero or negative, stops the block with an error. Axis ranges have their own parameter type (`wavelength_ranges`).
- Column scaling blocks for developers: mean-centring (`preprocess.mean_centre`), autoscaling (`preprocess.autoscale`) and Pareto scaling (`preprocess.pareto`). Means and standard deviations (ddof 1) are learned from the training rows and reused unchanged on new rows. Set `target` to `y` to scale the responses instead; `inverse_y` converts scaled predictions back to the original units. A column with the same value in every training row is centred, left unscaled, and reported with a warning.
- Calibration/test split blocks for developers: random split (`split.random`, optionally stratified by class or by y quantile bins, reproducible from a seed), Kennard–Stone (`split.kennard_stone`) and SPXY (`split.spxy`, distance on X and y together). Kennard–Stone and SPXY start from the two most distant samples or from the sample nearest the mean, and can measure distances on PCA scores instead of the raw spectra. When the data has groups (replicate spectra of one sample), each group stays entirely in training or in test. Each block outputs the training and test spectra and the split itself (`vibechem_core.data.FoldSet`).
- PLS regression block for developers (`model.pls`, NIPALS via scikit-learn, one or several y columns). X is only mean-centred unless `scale` is switched on. The fitted model keeps scores, loadings, weights, rotations, coefficients and the explained X and Y variance, and gives predictions for every number of latent variables from one fit. A maximum number of latent variables larger than the data allows is lowered to the largest possible number, with a warning; a fixed number that is too large is an error. Using the largest possible number warns that the model then equals ordinary multiple linear regression. When y was scaled by a scaling block, connecting that block's transform makes the predictions come out in the original y units.
- PLS regression can now use SIMPLS (`algorithm = simpls`, de Jong 1993) instead of NIPALS. For one y column it gives the same predictions; it follows the same rules for the number of latent variables. When SIMPLS runs out of numerical precision at high LV counts, the extra components are dropped with a warning. `vibechem_core.blocks.model.pls.vip` gives the Variable Importance in Projection of every variable from a fitted PLS model, at any LV count up to the fitted one.
- PLS-DA classification block for developers (`model.plsda`): PLS on one indicator column per class (two or more classes); each sample goes to the class with the largest predicted value, ties to the first class in label order. The predictions table gives the predicted class and one score per class.
- Cross-validation fold blocks for developers: k-fold (`validate.kfold`), venetian blinds (`validate.venetian_blinds`), contiguous blocks (`validate.contiguous_blocks`), leave-one-out (`validate.loo`), repeated k-fold (`validate.repeated_kfold`) and group k-fold (`validate.group_kfold`). Folds are made once and are reproducible from a seed. Leave-one-out leaves out one whole group at a time when the data has groups, and group k-fold never puts one group in both training and validation. The other schemes ignore groups and say so in their output. Asking for more folds than samples (or groups) is an error, not a silent switch to leave-one-out.
- Model metrics for developers (`vibechem_core.metrics`): RMSE, bias (positive means over-prediction), SEP, R², slope and intercept, RPD, RPIQ and the residual sum of squares for calibration, cross-validation and test sets, named as they will appear in results (`rmsecv`, `bias_p`, `press` …). Cross-validation RMSE is pooled over all out-of-fold predictions by default, or the mean of the per-fold values. For classification: confusion matrix, accuracy, per-class sensitivity and specificity, and ROC-AUC (one-vs-rest mean for more than two classes). A metric that cannot be computed, for example R² when every y value is equal, is reported as NaN with a warning; validation sets smaller than ISO 12099 recommends also give a warning.
- `vibechem-core` 0.1.0: the science library builds as one wheel for Windows, macOS and Linux. CI installs it on all three and checks that it reproduces the published gasoline PLS result (Mevik & Wehrens 2007). A reference test also reproduces the paper's full leave-one-out protocol with the library's own blocks.
- Cross-validation for developers: `validate.cv` cross-validates a PLS regression model on any fold block's folds. The engine re-fits the whole preprocessing and model chain on each fold's training rows, so nothing learns from the rows it is tested on. It reports the RMSECV curve for every LV count, its per-fold spread, the average over repeats and all CV metrics at the chosen LV count. The LV count is chosen by global minimum (default), the one-standard-error rule, a paired t-test, Wold's R criterion, the Haaland–Thomas F-test on PRESS or van der Voet's randomisation test (reproducible: its random seed comes from the run and is stored with the results). Folds that predict a row twice or never stop the block with an error, and folds that split groups give a warning. `vibechem_engine.runners.run_pipeline` runs such a pipeline on the process pool.
- `validate.cv` now cross-validates PLS2 and PLS-DA models too. With several Y columns it picks the LV count on the total prediction error in the model's own (scaled) units, reports each column's metrics separately, and warns when unscaled Y columns differ a lot in variance. For PLS-DA it picks the LV count on the error of the predicted class indicators and reports accuracy, sensitivity, specificity and ROC-AUC (averaged over classes with equal weights and by class size, optionally pooled), the class ratio, the error rate for every LV count, and a warning when a class is missing from a fold's training rows or the classes are very unbalanced. Its new `model` output is the full-data model at the chosen LV count.
- Nested cross-validation for developers: `validate.nested_cv` gives an honest error estimate for a tuned model. On each outer fold's training rows it makes inner folds with a fold block of your choice (`inner_folds`, default shuffled 5-fold) and runs a grid search there to pick the LV count and, if a search space is given, the preprocessing chain; the chosen chain and model are then refitted on the outer training rows and predict the outer validation rows. It reports the outer CV metrics and, per outer fold, the chain and LV count that were chosen. It has no model output: run `validate.cv` (or the grid search) on all rows for the model to keep. A wrong `inner_folds` block stops the node with `BLOCK_PARAM_INVALID`. The outer folds' inner searches share the CPU cores: when one outer fold cannot use all of them, the next outer folds start, with the same results as running them one by one.
- Preprocessing grid search for developers: `validate.grid_search` cross-validates every preprocessing chain of a search space (ordered slots such as scatter correction, baseline, smoothing and scaling, each with a "none" option) on the same folds, with the same model and LV rule as `validate.cv`. Repeated chains are run once. It returns a table with each chain and its CV metrics, and the best chain (lowest RMSECV at its chosen LV count). The default search space has 252 chains built from SNV, MSC, detrend, Savitzky–Golay derivatives, autoscaling and Pareto scaling. An unknown block in the search space stops the search node with `BLOCK_PARAM_INVALID`. A search with more than 1000 chains, more than 1000 LV counts, or more than 50000 chain × LV-count combinations is refused before anything runs. A new `n_jobs` setting (default: all cores minus 10, at least one) says how many workers the search may use; the run uses the smaller of that and the engine's workers for the steps that run the search. One worker may run at most 1000 chain × LV-count combinations: a larger search with one worker is refused (`BLOCK_PARAM_INVALID`, reason `serial_too_large`), and with several workers it runs with the warning `VALIDATION_SEARCH_PARALLEL_ONLY`.

### Fixed
- `scripts/check.py` no longer crashes with `UnicodeEncodeError` when its output goes to a console that cannot show every character (for example a Japanese cp932 Windows console); such characters are printed as `?` (#42).
- SPXY split with groups now stops with `BLOCK_CONSTANT_RESPONSE` when every group has the same mean response. Before, it quietly returned the first rows in input order as the test set. All split blocks now reject an empty group label with `BLOCK_INPUT_REQUIREMENT_MISSING`, as the grouped cross-validation schemes already did; before, unlabelled rows were treated as one group (#58).
- PLS with several Y columns (NIPALS, also PLS-DA) now iterates each component to full precision. Before, it stopped early, so weights, scores, predictions and VIP could differ from other software in the fifth significant digit. PLS with one Y column is unchanged. Reference values from R (`pls`, `plsVarSel`, `mixOmics`) now check SIMPLS and VIP.
