# vibechem-engine (`vibechem_engine`)

**Status:** walking skeleton plus the first Phase 2 pieces: `vibechem_engine.api` (T0.09), `vibechem_engine.ports` (T2.01), `vibechem_engine.graph` (T2.02), `vibechem_engine.formats` (T2.03) `vibechem_engine.compiler` (T2.04, leakage rules T2.05) `vibechem_engine.cache` (T2.06), `vibechem_engine.executor` (T2.07) and `vibechem_engine.scheduler` (T2.08, crash recovery T2.09) and `vibechem_engine.runners` (CV runner, T2.10a).

**Purpose:** runs pipelines. It covers port types, the pipeline graph and file format, the compiler, cache, executor, scheduler, runners, projects, the local HTTP/WebSocket API and the CLI.

**Public API:**
- `python -m vibechem_engine.api [--testdata-dir PATH]` — start the HTTP API (DATA_MODEL.md §1 "Start-up"); `VIBECHEM_DEV=1` allows the Vite dev server origin. The desktop app ships this entry point frozen with PyInstaller (`scripts/build_engine.py` → `vibechem-engine[.exe]`; `__main__` calls `multiprocessing.freeze_support()` first).
- `vibechem_engine.api.schemas` (T1.03): pydantic models of the `GET /blocks/{block_id}` object (`BlockDetail`, parameter entries discriminated by `type`), i.e. DATA_MODEL.md §5 as a model; `BlockDetail.model_json_schema()` is its JSON Schema. Not yet served by a route.
- `vibechem_engine.ports` (T2.01): `PORT_TYPE_REGISTRY` (DATA_MODEL.md §4.1), `COMPATIBILITY` (§4.4), `is_compatible(from_type, to_type)`, `edge_rule(from_type, to_type)` (the conversion rule, `None` for equal types, `ValueError` for an incompatible pair), `port_types_payload()` (`GET /port-types` body). Unknown type names raise `ValueError`.
- `vibechem_engine.graph` (T2.02): `validate_graph(pipeline, registry)` checks a pipeline document (DATA_MODEL.md §2.6) against the blocks' ports and returns every §4.4 graph problem as a `GraphIssue` (`to_dict()` = one `POST …/validate` issue): `PIPELINE_PORT_TYPE_MISMATCH`, `PIPELINE_INPUT_MULTIPLE_EDGES`, `PIPELINE_REQUIRED_INPUT_MISSING`, `PIPELINE_CYCLE`. Unknown block, node or port and a repeated `node_id` raise `ValueError`.
- `vibechem_engine.formats` (T2.03): the file formats of DATA_MODEL.md §6 as strict pydantic models — `PipelineFile` (`load_pipeline`/`save_pipeline`), `ProjectFile` (`load_project`/`save_project`), `ModelManifest` + `ModelPackage` (`read_model`/`write_model`, the `.vcm` zip with states in the `save_state` layout). Invalid files raise `FormatError` (`PIPELINE_FILE_INVALID`, `PROJECT_FILE_INVALID`, `MODEL_PACKAGE_INVALID`, `params.reason` per §6.1); missing files raise `OSError`. `formats.migrations`: `CURRENT_VERSIONS`, `@migration(kind, from_version)`, `migrate()` (§6.5). JSON Schemas in `formats/schemas/`, kept in sync by `tests/formats/test_pipeline.py` (`VIBECHEM_UPDATE_SCHEMAS=1` rewrites them).
- `vibechem_engine.compiler` (T2.04): `compile_pipeline(pipeline, registry)` → `CompiledPipeline` (`tasks`, `fold_plans`, `issues`). Stateless blocks become `run` tasks, fitted blocks `fit` + `apply` (the fit task's one output `state` is what the block's `Model`/`Transform` ports carry); implicit §4.4 conversions are the task input's `rule`. A node with a connected `refit_per_fold` input gets a `FoldPlan`; the runner calls `plan.expand(fold, repeat)` per fold for `select` + per-fold `fit`/`apply` tasks (fit on `train` rows only). `PIPELINE_FOLDS_SOURCE_MISMATCH` when the re-fitted subgraph is not downstream of the fold source (DATA_MODEL §4.6). `fold_rows(data, fold, part)` selects fold rows by `row_index` via core `SpectralDataset.rows`. `FoldPlan.scope()` is what the leakage rules check per fold.
- `vibechem_engine.compiler.leakage` (T2.05): the static `PIPELINE_LEAKAGE` rules `compile_pipeline` applies — `fitted_before` (fitted block upstream of a fold source or of a used `train`/`test` split output) and `row_leaks` (row provenance: a fit input with rows outside its training subset or from a `test` output, inside or outside the folds; a `Model`/`Transform` applied to test rows it may have been fitted on). Suite in `tests/leakage/` (rules, noise data vs scikit-learn `Pipeline`).
- `vibechem_engine.cache` (T2.06): `result_key(task, output, *, block_id, block_version, params, input_keys, seed)` → `res_` + SHA-256 (recipe and folder layout: DATA_MODEL.md §6.6). `ResultCache(root, cap_bytes)`: `get(key)` → `State | None` (a damaged entry is deleted and returns `None`, so the task is recomputed), `put(key, state)` → bytes freed by LRU eviction (for `cache.evicted`), `clear()`, `in`, `len`, `size_bytes`. Entries use the core `save_state` layout plus `entry.json` checksums; no pickle. One engine process owns the folder; not thread-safe.
- `vibechem_engine.executor` (T2.07, ARCHITECTURE §3.4): `Executor` protocol (`max_workers`, `submit(fn, *args)` → `Future`, `restart()` = kill the workers and start fresh ones, `shutdown()`); `ProcessExecutor(max_workers, spill_dir, *, idle_timeout=300)` = warm loky pool, BLAS and OpenMP capped at 1 thread per worker (`OPENBLAS_`/`OMP_`/`MKL_NUM_THREADS`, `VECLIB_MAXIMUM_THREADS` = 1 set before anything loads, so SciPy's own OpenBLAS is covered too; threadpoolctl on what NumPy loaded), context manager (`shutdown(kill=True)` on an exception, so the rest of the queue is not run). `share(array)` saves an array of at least `SHARE_THRESHOLD_BYTES` (1 MiB) once as `.npy` in `spill_dir` and returns a `MappedArray`; as a top-level `submit` argument the worker gets it as a read-only `np.memmap` (smaller arrays are returned unchanged and pickled). Shared files are deleted on `shutdown()`. `task_seeds(root_seed, n)` → one 53-bit `int` per task (child *i* of `SeedSequence(root_seed).spawn(n)`; call once per run over the whole task list in a stable order). `loky_freeze_support()` is called by `api/__main__.py` before `multiprocessing.freeze_support()`. Task functions must be importable by the workers (module-level).
- `vibechem_engine.scheduler` (T2.08, ARCHITECTURE §3.4–3.6): `run_jobs(jobs, executor, *, root_seed, cores=None, memory_budget_bytes=None, emit, cancel, clock)` → `RunResult` (`status` `succeeded`/`failed`/`cancelled`, `duration_s`, `results` and `errors` by task id, `failed_nodes`, `unfinished_nodes`). A `Job` (task id, node id, module-level `fn`, `args`, `deps`, `memory_bytes`, `threads`) runs in a worker as `fn(seed, *args, *dependency results)`. Running jobs stay within `cores` (summed `threads`), `executor.max_workers` and `memory_budget_bytes` (summed estimates, `estimate_memory(*arrays)` = 2 × input bytes; a job over the budget runs alone); dispatch is FIFO in readiness order. Job *i* of the list gets seed *i* of `task_seeds(root_seed, len(jobs))`, so pass one stable list per run (R57). A failure skips the job's dependants and is logged with its traceback; an executor error (broken pool) or an `emit` error is raised once the running jobs end. Setting `cancel` (`threading.Event`) stops dispatch and lets running jobs finish; workers still busy `cancel_timeout_s` (5 s) later are killed (`executor.restart()`). Recovery (T2.09, ARCHITECTURE §3.6), one retry per job, run alone: a dead worker (`TerminatedWorkerError`) restarts the pool and retries every job that was running, with its `Job.fallback` (`Fallback(fn, block_id, kernel)`, the Python reference of a native kernel; `native.fallback` event) if set; a `MemoryError` halves the concurrency cap (`memory.throttled`) and retries, a second one is the node error `RUN_OUT_OF_MEMORY`. `emit(type, data)` gets DATA_MODEL §3 `node.state`, `node.progress`, `run.progress` (≤ 4/s, last always sent) and `memory.throttled`; the caller sends `run.started`/`run.finished` and sets `unfinished_nodes` back to `idle`/`stale`. Raises `ValueError` for a repeated task id, unknown dependency, cycle or `threads` outside `1..cores`.
- `vibechem_engine.runners` (T2.10a): `run_pipeline(compiled, pipeline, registry, sources, executor, *, root_seed)` → `PipelineRun` (`status`, `outputs` = `TaskOutput(values, warnings)` by task id, `errors`; `output(node_id, port_id)`, `state(node_id)`). Runs the compiled tasks on the scheduler in four stages: top-level tasks not needing a validation node (data nodes from `sources`), the fold tasks of every `FoldPlan` once its `Folds` are known (`select` by `row_index`), each validation node in-process with `fold_runs` (per fold: the state feeding `refit_per_fold` and that model's first input on the validation rows; core `validate.cv`), then their dependants. A task in a worker is `execute_task(seed, spec, *deps)`: block warnings are recorded and returned. One seed root per stage from `root_seed`. A stage with a failure ends the run (`failed`/`cancelled`). Implicit §4.4 conversions are not executed yet (`NotImplementedError`); compile errors raise `ValueError`. T2.10c: a `validate.grid_search` node is expanded first (`runners.search.expand_search`: one `validate.cv` branch per candidate chain, node ids `<search>.c<i>…`, the expanded pipeline compiled again); in stage 3 the search node gets `candidates` (chain, branch `Results`) and the branches' warnings; a branch error is also reported on the search node; a bad `search_space`, a search above the N31 caps or above the serial limit with one worker fails the run with `BLOCK_PARAM_INVALID` on the search node; w = min(effective `n_jobs`, `executor.max_workers`) is the `cores` budget of every stage holding branch tasks, and N·M > 1000 with w > 1 adds `VALIDATION_SEARCH_PARALLEL_ONLY` to the search node's warnings (option A). T2.10d: a `validate.nested_cv` node is expanded like a search (one branch per candidate on the outer folds, `expand_search` accepts any block with grid-search params); after stage 1 one sub-run of `runners.nested.inner_pipeline` per outer fold (sources = the outer training rows of the fold source stream; an inner `validate.grid_search` on the `inner_folds`) gives the choice; stage 2 expands only the chosen branch per outer fold, the branches' other tasks never run; stage 3 gives the node `fold_runs` and `choices`. Bad `inner_folds` → `BLOCK_PARAM_INVALID` node error before anything runs.
- `vibechem_engine.api.create_app(token, *, testdata_dir, dev=False)` — the FastAPI app: `/api/v1/health`, `/api/v1/blocks` (static SNV entry), temporary `/api/v1/skeleton/run` (§2.12, removed in T4.01).

Later: the Python API and CLI (T2.11) and the rest of the HTTP/WS API in `docs/DATA_MODEL.md`.
