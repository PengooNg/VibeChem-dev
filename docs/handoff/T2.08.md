## Plan
**Goal (Done when):** core budget, memory estimator, cancellation and progress events tested.

**Assumptions**
- The scheduler is generic: it runs `Job`s (task id, node id, dependencies, a module-level function, static args, memory estimate, thread width) on any `Executor`. Binding compiler `Task`s to block calls, fold expansion and the cache lookup stay with the runners (T2.10). A job function is called in the worker as `fn(seed, *args, *dep_results)` (dep results in `deps` order).
- Seeds: `task_seeds(root_seed, len(jobs))` once per run over the caller's job list, by list position. Dispatch order never changes a job's seed, so readiness-order dispatch does not change results (R57 (a) unchanged; no QUESTION stop). A multi-stage runner must keep one stable list (README note).
- Core budget: running jobs' `threads` sum ≤ `cores` and running jobs ≤ `executor.max_workers`; a job with `threads > cores` is a `ValueError` (the caller sizes kernels).
- Memory: the caller passes `memory_budget_bytes` (settings `memory_budget_fraction` × `/system` `memory_available_bytes`; measuring free RAM lands with T4.01 / T2.09). `estimate_memory(*arrays)` = 2 × input bytes (input + one working copy) — heuristic, not METHODS. A job over the budget runs alone. When memory alone holds a ready job back, `memory.throttled {old_workers, new_workers}` is emitted (on change only).
- Events: `emit(type, data)` callback with DATA_MODEL §3 types and fields: `run.started`, `node.state` (`queued`, `running`, `done`, `error` + `code`/`message_key`/`params` for a `VibeChemError`), `node.progress` (nodes with > 1 job), `run.progress`, `memory.throttled`, `run.finished` (`status`, `duration_s`, `failed_nodes`). `seq`/`ts`/`run_id` envelope belongs to the WebSocket layer (T4.02). Progress ≤ 4/s per node and for the run; the last update always goes out.
- Failure: a failed job's descendants are not run; independent branches continue (§3.6). Cancel: `cancel()` (thread-safe) stops dispatching, waits for running jobs, `run.finished` `cancelled`. Killing stuck workers after a timeout is T2.09. Nodes left unfinished are returned in the result (`unfinished`) so the run route sets their state (it knows the prior state: `idle` or `stale`).
- R57 (b) (`release()` / sweep of shared files) moves to the step that keeps one pool across runs (T2.10 / T4.01): the scheduler does not share arrays.
