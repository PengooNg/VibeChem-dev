## Plan
**Goal (Done when):** `/blocks/{id}`-shaped JSON generated for the dummy blocks and validated against DATA_MODEL.md §5.

**Assumptions**
1. `vibechem_core` may not import pydantic: TECH_STACK.md §3.1 lists it only for `vibechem_engine`, and core's `pyproject.toml` does not depend on it. Route: core exports plain JSON dicts from `Param` and validates parameter *values* in plain Python; the §5 shape is written as pydantic models in `vibechem_engine/api/schemas.py` (engine may import pydantic; TECH_STACK §1.2 lists pydantic for "API models, parameter schemas"), whose JSON Schema generation is the reused part. Engine tests validate the dummy blocks' export against these models.
2. Implemented parameter types now: `int`, `float`, `bool`, `enum`, `string`. `range`, `wavelength_range`, `column_ref`, `list` get their §5 shape but are marked *reserved*: `Param` refuses them until the first block that needs one (A2).
3. Cross-field constraint keeps the §2.3 string form, restricted to `"<this param> <op> <other param | number>"`, `op` ∈ `< <= > >= !=`, parsed by a regex (no `eval`).
4. `visible_if` = `{"param_id": <other bool/enum param>, "values": [...]}`; hidden parameters keep their value and are still validated.
5. One new error code `BLOCK_PARAM_INVALID` (422 in pipeline validation / node error), defined in `core/block`, with params `param_id`, `reason` (`unknown`, `type`, `below_min`, `above_max`, `not_a_choice`, `not_odd`, `constraint`), plus `value`/`constraint` when useful.
6. `/blocks/{id}` fields `implementation`, `help_key`, `custom_panel`: new optional `Block` class attributes `implementation` (default `("vibechem", "<module>.<qualname>")`; `TransformerBlock` defaults to the estimator's library) and `custom_panel` (default `None`); `help_key` = `blocks.<id>.help`. `label_key`/`tooltip_key` of a param default to `blocks.<block_id>.params.<param_id>` (+ `.tip`).
7. `None` defaults are refused (no nullable type in §5 yet).
8. No HTTP endpoint is added (the real `/blocks/{id}` route comes with the API steps).

**Reuse scan + estimate**
| Option | What it covers | Licence / maintenance | Effort | Risks |
|---|---|---|---|---|
| pydantic models in core (`create_model` per block) | export + value validation | MIT, active | 3 cp | breaks TECH_STACK §3.1 boundary → needs doc change + K |
| Wrap pydantic in engine (shape models + JSON Schema) + small export/validation in core | everything | MIT, active, already an engine dependency | 4 cp, ~5 files, ~450 lines incl. tests | odd_only / constraint / visible_if need custom checks either way |
| Build all by hand (JSON Schema dict + jsonschema) | everything | jsonschema not in stack | 4 cp | new dependency |
Recommendation: option 2 (wrap pydantic where the boundary allows; ~80 lines of plain-Python value checks in core). Size M as in TASKS.md.
