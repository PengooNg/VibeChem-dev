## Plan
**Assumptions**
- Leakage rules are static (compile time, on the user graph), as ARCHITECTURE §3.2 says: "any connection that would feed validation/test rows into a fit task is rejected at compile time". No runtime row checks here.
- Row provenance is derived from graph ancestry: every node without input edges is a data source; a stream carries the sources and the row subsets (`<split>.train` / `<split>.test`, `<cv node>.train` inside a fold) on its path. Conservative: an input from the same data source that did not pass through the fit's training subset is leakage even if a block would only use part of it (R39 wants exactly that for MSC `reference`). Inputs from another source (e.g. a separate reference dataset) are allowed.
- Any fit task that sees rows of a hold-out `test` output is leakage (DATA_MODEL §4.6: "a later fit on test rows is still detected").
- The existing T2.04 rule (fitted block upstream of the fold source) moves into `compiler/leakage.py` unchanged.
- Not in scope (not in "Done when"): runtime `validate.test_set` overlap with `Model.fitted_rows` (block does not exist yet; `fitted_rows` is not implemented); `leakage_safe` badge/API; R25 group warning wiring (runtime, engine step that records block outputs) — R25 stays open, noted.
