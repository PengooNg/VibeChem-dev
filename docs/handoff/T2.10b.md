### Open questions (blocking, before code)
Q1. **How does a preprocessing-chain search enter the graph?** DATA_MODEL §4.6 fixes validation as one block whose `refit_per_fold` port is fed by a fixed subgraph; pengoo searches over *chains of step types* (scatter, baseline, denoise, smooth, scale; each with a "None" option). No block id, port or param for the search exists in DATA_MODEL (only `Results.kind = search`, `candidates`). Options:
  - A. A `search_space` param on the search block (JSON: ordered step slots, each a list of `{block_id, params}` options, "none" allowed); the engine builds each candidate chain between the fold source and the model block. Close to pengoo; candidates are not nodes on the canvas.
  - B. A grid over params of nodes already in the refit subgraph (`grid`: `{"<node_id>.<param>": [values]}`), plus a per-node `bypass` option for "None". Fits the graph and the fold-level cache (each variant = content hash); a step-type choice (MSC vs SNV) needs two nodes with bypass.
  - Recommended: **A** for preprocessing chains (it is what pengoo and F-43 mean; the default search space becomes a JSON file from registered blocks, as TECH_STACK §11.2 says), B later for hyperparameters only if needed.
Q2. **Inner folds of nested CV:** DATA_MODEL §4.6 leaves "an inner `inner_folds: Folds` input or an inner scheme parameter (decided in T2.10)". A `Folds` input made on the full data cannot be the inner folds (they must be made on each outer training set). Recommended: **inner scheme parameter** (`inner_folds`: `{block_id, params}` of a fold block, run by the engine on each outer fold's training rows; groups follow the outer data).
